# Telegram Channel DOX

## Purpose

- Own Telegram polling/webhook intake, live authorization, media handling, activity, identity mapping, and outbound delivery.

## Local Contracts

- Re-resolve and validate the current allow-list at startup and every inbound/outbound/provider boundary; stale identity mappings or credentials never grant access, and authorization loss terminates useful traffic.
- Persist only minimal identity learned from an authenticated private update, keep webhook secrets and URLs out of status, and permit only teardown `deleteWebhook` after revocation.
- After a successful `getMe`, register the application-supplied command menu best-effort through `setMyCommands` in the `all_private_chats` scope before polling or webhook startup. Reapply global live authorization through the ordinary provider wrapper, never register a group scope, treat provider failure as non-fatal, and propagate authorization loss or caller cancellation; after revocation, retain `deleteWebhook` as the only provider exception.
- Stream bounded media privately, deliver only the final response/error plus validated directives, and keep typing references per route, best-effort, serialized, and bounded. When the default-on live `speech.transcript_echo` is enabled, each successful transcription also echoes once to the same chat or topic as a standalone pre-dispatch message that contains only the shared generated-transcript block and replies to the originating voice or audio message; the echo is not an agent response, and its delivery failure never affects the turn. Translate proactively routed recovery activity through the same refresher and stop it before recovered terminal delivery.
- Build and parse routes only through the strict canonical conversation grammar: `TG-<positive-user-id>`, `TG-<positive-user-id>-topic-<positive-thread-id>`, `TG-group-<negative-chat-id>`, and `TG-group-<negative-chat-id>-topic-<positive-thread-id>`. Non-canonical origins fail closed. Absent threads and the General topic (ID 1) canonicalize to the base conversation and outbound thread ID 0, preserving existing identities; thread IDs of at least 2 select an independent durable conversation and harness session.
- Reapply the current allow-list, verified username mapping, and `group_mode` policy immediately before every route-bound provider call and again before the single bounded rate-limit retry. Private topics authorize through their base numeric user, group topics through the current group policy, and thread IDs never grant authorization on their own.
- Keep every outbound family in its originating route: replies, terminal errors, typing actions, welcome messages, transcript echoes, native photo/document attachments, proactive events, and recovery delivery carry the route's `message_thread_id` when it addresses a topic, and base or General-topic delivery omits it.
- Deliver replies as independently valid `sendMessage` HTML chunks produced by the markdown chunker: at most 4096 parsed-visible Unicode code points per message and 32768 parsed-visible code points across at most eight messages per reply. Formatting stays balanced, an entity spelling or Unicode code point is never split, grapheme boundaries are preferred while the remaining reply budget allows, and an over-budget reply ends with the deterministic visible truncation marker while complete durable history stays intact. Retry one rejected HTML chunk once as plain text only for a provider entity/HTML parse rejection; honor one provider 429 with a usable `retry_after` up to 60 seconds and otherwise fail without waiting or looping. Transcript echoes use the same chunk and reply budgets through `TelegramPlainChunks`, which HTML-escapes literal transcript text without Markdown interpretation so user speech renders exactly as transcribed.
- Carry the authenticated chat/message tuple as private stable source correlation through application acceptance so polling/webhook redelivery cannot duplicate work.
- Rename a private topic at most once per conversation and process. The automatic path (`force=false`) is unconditional on its first trigger, so a newly created thread is never left as "New chat" and the user owns the title after Spynel renames it; every successful rename, including `TOPIC_NOT_MODIFIED`, is marked in a bounded 1024-entry in-memory set with simple eviction, only a conversation already in that set is skipped, and a failed rename is not marked. A restart clears the set and eviction can re-enable one rename beyond 1024 conversations, both accepted edges. No title-state tracking, `forum_topic_created`/`forum_topic_edited` handling, or `is_name_implicit` logic exists.
- `RenameConversation` renames one private topic through `editForumTopic` after parsing the canonical route and rejecting base chats, groups, malformed routes, and invalid labels, and every provider call plus its single bounded retry reapplies live authorization. An automatic repeat for an already-renamed conversation is a silent no-op success, a forced rename from `/pi name` always reaches the provider even after Spynel renamed the topic, a `TOPIC_NOT_MODIFIED` 400 counts as success because it proves the requested title is live, any other provider error propagates unmarked, and a successful or idempotent rename marks the conversation.
