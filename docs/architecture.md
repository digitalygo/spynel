# Architecture

Spynel is a classic, non-AI program. Its architecture keeps deterministic communication, state, runtime oversight, and lifecycle management separate from the intelligence supplied by external coding harnesses. This boundary lets Spynel exploit improving harness capabilities instead of duplicating or competing with them.

Authenticated transport and loopback admission is the workspace authorization boundary for live jobs, logs, and durable history inspection. The shared application handler returns one global runtime job set and bounded privacy-safe projections to Telegram, WhatsApp, TUI, CLI, and API callers; it never treats caller conversation, creation channel, or `notify.origin` as an ACL. Notification origin remains independently validated routing metadata for outbound delivery.

| Boundary | Ownership |
| --- | --- |
| `agentdocs` | Curated offline topics, stable references, bounded pagination/search, versioned JSON, and shared help metadata. |
| `cli` | Interactive/server composition plus bounded non-visual automation commands and output contracts. |
| `core` | Transport-neutral messages, streamed events, form screens, controls, and slash-command metadata. |
| `config` | Typed defaults/validation, atomic private persistence, and newest-only live snapshots. |
| `app` | Shared commands, screen construction, configuration save/reload, per-conversation dispatch, status, logs, jobs, onboarding, and branching. |
| `channel` | TUI/Telegram/WhatsApp adapters plus isolated hot-reload supervision. |
| `harness` | Harness contract/capabilities, catalog, idle-only implementation switching, commit-ordered model dispatch snapshots, Codex app-server, Claude Code print mode, Agent Zero CLI capability discovery over shared ACP, Pi RPC, and shared ACP v1 stdio sessions. |
| `history` | Append-only JSONL, bounded reverse reads, discovery previews, clearing, and point-in-time branch copies. |
| `instance` | Cross-platform primary-server election, lock-free atomic lease discovery, heartbeat renewal, and fenced stale takeover. |
| `localapi` | Authenticated loopback TUI/CLI-to-owner streaming, typed status, and bounded shared-state snapshots. |
| `media` | Private streamed attachment commits, validated outbound file directives, serialized Parakeet processing, and coordinated per-user managed speech models. |
| `markdown` | GitHub-flavored terminal rendering plus Telegram HTML and WhatsApp-native conversion. |
| `startup` | Reversible workspace-specific systemd, launchd, and Task Scheduler registration. |
| `theme` | Validated semantic palettes, embedded YAML assets, and no-clobber workspace installation. |
| `extensions` | Trusted Git installation and bounded executable-hook protocol. |
| `updater` | Installation-local npm/GitHub ownership, bounded checks, validated immutable standalone bundles and stable restart paths. |
| `workspace` | Embedded editable configuration and DOX templates plus private directory creation; built-in themes remain owned by `theme`. |

`cmd/spynel` is composition only. A channel translates external traffic into `core.Message` and calls the application; it never knows which coding-agent protocol is active. The application depends only on `harness.Harness`.

Live configuration uses a serialized save-and-reload boundary. The store validates a complete candidate, atomically replaces canonical YAML, reloads that file into the shared process snapshot before returning, and publishes the refreshed value. Runtime consumers read that snapshot for subsequent operations; only owners with derived cached state receive small direct refresh hooks. Channel supervision reconciles published snapshots without replacing the running process, and active communication work may finish under its already-admitted state.

Spynel no longer runs Markdown task or goal workflows, review or recovery loops, a semantic heartbeat, a notification agent, or autonomous unresponded-message scans. Existing `.spynel/tasks`, `.spynel/goals`, `.spynel/prompts`, and `.spynel/instructions` content remains untouched and inert on disk; no runtime path creates, inspects, composes, or injects those documents into a harness prompt, and no `spynel instructions` command exists. The retired workflow configuration keys are ordinary unused keys that are ignored on load and omitted by the next canonical save.

`agentdocs` is intentionally below both `cli` and `app`. Its reviewed Go catalog contains no workspace or network readers. `spynel docs` therefore works before initialization and while disconnected, and its output cannot leak histories, leases, credentials, origins, or environment values. The concise `/help` index derives its stable topic labels from the same catalog while keeping channel-facing bodies short. Live state remains behind typed application status, job, log, and history boundaries rather than being copied into static documentation.

## Screen contract

A `core.Screen` is a transport-neutral form or action list rendered instead of chat. It may also provide named tabs plus an active index for wizard progress, while a control's optional `Section` inserts a labeled group rule before that control. A sectioned disclosure merges its clickable Show/Hide label into that rule instead of rendering a duplicate heading and button. The TUI preserves transcript/composer state while a screen is open. A child screen names its parent; the TUI snapshots and restores the parent's controls, unsaved edits, focus, disclosure state, and scroll position when the child completes or is escaped. Ctrl+C is a global surface exit: from any non-required screen or modal it drops the entire in-memory screen stack and returns directly to preserved chat; required setup exits the application. The TUI also owns a reusable centered modal primitive above `core.Screen`: while visible it captures other keyboard events, renders the underlying screen in place, and resolves one selected outcome before returning control. Dirty-exit confirmation for `/config`, `/telegram`, and `/whatsapp` offers Save through the ordinary validated persistence path, Discard without persistence, and safe-default Keep editing. Its semantic-muted control hints occupy the lower border, with rule segments as separators and a blank interior row above. Successful persistence restores chat; failure preserves the live form. Scalar form controls and text commands use the same `config.Setting` keys, so validation and persistence do not diverge between local and remote setup.

The `theme` boundary validates complete semantic color maps from `.spynel/themes` and supplies twelve stock palettes, six light and six dark, with two explicitly color-blind-friendly palettes in each group, when an upgraded workspace has no theme files. A stable stock-order registry keeps `spynel` and `hack-the-box` first and second, groups all six dark palettes before all six light palettes in their approved relative order, and sorts user palettes after stock entries. Stock metadata and measured luminance enforce the matrix; contrast tests cover ordinary and muted text, layered surfaces and selections, selected controls, status accents, borders, inline code on elevated surfaces, and fenced code on the page canvas. A collection regression computes mean CIE 1976 Lab distance across twelve meaningful semantic roles for every same-appearance pair, while accessible palettes additionally simulate severe protanopia and deuteranopia and require status separation. These checks support rather than replace identical-fixture PNG and contact-sheet review. Existing custom themes may omit the newer metadata. Renderers consume semantic values rather than palette literals, so the continuous main background, muted-user-accent upper/lower half-height ribbons, bordered composer/pickers, unframed chat/forms, layered controls, scrollbars, chat labels, errors, and terminal Markdown switch together. Fenced code uses the semantic `code` role in truecolor rather than Glamour's process-global Chroma registry, and each theme change rebinds the textarea's cached style pointer so code and placeholder colors cannot leak from a prior palette. The primary accent owns Spynel identity; `You` uses the user accent directly, while ribbons blend that accent evenly with the page background to reduce their visual weight without adding another palette role. Messages share that canvas instead of receiving individual background cards. The shared application persists theme names; the TUI alone owns temporary arrow-key preview state.

The TUI event loop has a 16 ms normal-operation target and a 100 ms stressed-fixture ceiling. It never performs theme discovery or pasted-file probing, copying, or syncing itself. One cancellable paste command owns that work at a time; up to eight later pastes wait in order, Ctrl-C cancels the active import and clears its queue, and further admission remains visible literal composer text instead of being dropped or spawning more workers. Enter waits until placeholder imports settle, so a path can never be dispatched before its private attachment copy is committed. Streaming Markdown likewise has one render in flight. Deltas received during it update a bounded, control-sanitized plain preview and coalesce viewport publication to at most 60 Hz; results are accepted only for the current width and theme and only when their source is still a prefix of the live stream. An accepted current result is reused until stream content, width, or theme changes, and a superseded result waits one publication interval before replacement so a continuous delta burst cannot create a formatter loop. Large transcript rerenders caused by resize, theme, or history changes use the same one-in-flight/stale-result pattern. This keeps typing, scrolling, resize, and cancellation independent of slow disk or Markdown work while preserving final content and ordering. Finalized transcript Markdown is cached incrementally, and spinner-only ticks reuse it. `Update` calls over 16 ms, theme/paste/render work over 100 ms, and paste-queue pressure are rate-limited to one report per five seconds and forwarded through the authenticated loopback API into the owner's structured runtime logger; diagnostics never write directly to the alternate-screen terminal or trigger on frames. The mixed-load regression fixture exercises that update path while bounded workers perform Markdown/layout, runtime logging, durable history appends, notifications, and channel activity; it reports event-loop p95 latency, maximum UI/background queue depth, and peak/final goroutine counts and can emit the standard Go CPU, allocation, block, mutex, scheduler, and goroutine profiles.

The composer panel, textarea, and cursor use the same inner cell width. Its visible height follows the textarea's word-aware, grapheme-width rows on the update that creates or removes them, including the fresh cursor row reserved at an exact fit; Up/Down continues through wrapped rows and reaches the first/final insertion boundary without hiding the cursor. Reported terminal width is also a hard frame boundary: the viewport, textarea, ribbons, forms, and pickers never impose a wider synthetic minimum, and cosmetic horizontal insets yield before content on unusually narrow terminals so every emitted row fits while the cursor and any feasible composer border stay visible. Below the minimum full-canvas height, history and inline pickers yield their rows, the textarea adopts the remaining physical composer capacity, and its private viewport reanchors to the cursor-bearing tail in the same resize update; header, exact composer border, and footer remain inside the terminal. Composer growth reduces the history viewport by the same row count. If history is detached, its offset moves by that exact delta (and reverses on shrink) to preserve the reading anchor; legitimate tail-follow remains attached and recent manual upward scrolling still suppresses it for two seconds. Terminal resize, asynchronous Markdown completion, streaming, and notifications keep their separate anchor policies. User prose preserves repeated authored spaces and indentation, moves any fitting word or number intact to a fresh row, and hard-wraps only genuinely overwide tokens at grapheme boundaries. Spy streaming and finalized Markdown share one effective width and source-preserving renderer, so styling, role prefixes, padding, and the scrollbar are each accounted for once without synthetic punctuation or continuation spaces.

Terminal Markdown parses prose before adding render-only wrap hints. Ordinary letter-based ASCII-hyphen compounds that fit the effective row therefore move intact to the next row when necessary, while URLs, command flags, subtraction, list syntax, code, and Unicode dash characters retain their original semantics. Compounds wider than the effective row receive bounded hard-wrap opportunities, and every private hint is restored or removed before ANSI output; persisted history and copied source remain unchanged.

Initialization is a required screen because no application service exists before `.spynel/config.yaml`. Bare interactive startup first canonicalizes its launch directory. When that directory is uninitialized but ordinary discovery finds an initialized ancestor, a required three-action screen runs before primary election, service construction, channels, chat, or workspace writes. Its default parent action changes CWD to the discovered root; its local action calls the existing `workspace.Init` path with the original canonical launch root; exit paths mutate neither workspace. Explicit configuration and noninteractive commands bypass this screen and preserve deterministic discovery. The workspace root owns one fixed `.spynel` state directory, and configuration paths continue to resolve from that workspace root rather than from the nested file's directory. Configuration loading accepts only that canonical path and validated current settings; unused configuration keys are ignored on load and removed on save. Once `workspace.Init` succeeds, the same process loads the new project. It enters the welcome/chat surface when any non-custom catalog harness is detected, otherwise it opens the coding-harness chooser first. Interactive `spynel init` follows the same path; `--no-start` is the explicit automation mode. Welcome, configuration, harness/model selection, WhatsApp QR pairing, and conversation browsing use the same screen machinery.

## Conversation dispatch

Harness chat dispatch injects no Spynel persona, workflow, documentation, scope-discipline, honesty, dispatcher, or role instruction sections. Pi receives the raw accepted user text; its native system prompt, resources, extensions, skills, prompt templates, context files, provider settings, and project trust decisions remain authoritative. Every other harness receives the bounded provider-neutral history context instead, plus the outbound-attachment directive on Telegram and WhatsApp. A Telegram Pi RPC session alone loads one embedded Spynel Pi extension additively with `--extension`; the extension is materialized as a private file under `.spynel/runtime`, and its `before_agent_start` writes exactly one namespaced `spynel_telegram` section into Pi's structured system prompt: the user sees final replies only, so any clarification or approval request must be one final question that ends the turn, and the next user reply continues the same Pi session with no artificial pause state. The additive load keeps Pi's ordinary global and trusted-project `SYSTEM.md` and `APPEND_SYSTEM.md` discovery and resources active and adds no model or agent turn. The note is prompt guidance, not an enforcement boundary: a user extension that returns a forced prompt can override it, and extension-triggered model runs may bypass `before_agent_start`, so Spynel claims no model-compliance guarantee. Spynel still cancels blocking Pi extension UI dialogs so a headless turn cannot stall.

Known Spynel slash commands remain deterministic and routed through the shared application service; a known command that refuses a surface or lacks authorization still refuses. Unrecognized slash input is not categorically rejected: when the active harness accepts native conversation input, the raw spelling and arguments reach the harness, so Pi can expand its own native skill, prompt-template, and extension commands through its ordinary prompt pipeline. A harness without that capability receives the ordinary `Unknown command` reply. The Telegram Pi system-prompt note is written by one additively loaded embedded extension and is never prepended to slash user input.

The current user message is always delivered. Pi ordinary conversations deliver only that raw current entry because the provider session retains the conversation and manages its own context. Every other harness receives the bounded provider-neutral history seed unless the optional `ConversationContextProvider` capability reports a retained conversation, in which case only the current entry is delivered; on that path, a fresh session, a different harness, a missing or non-regular session file, a closed or unavailable harness, or any uncertain state keeps the bounded seed because false is always safe. Zero history limits disable only prior-history seeding.

Natural-language follow-ups use the active conversation session. Codex and Pi steer through their native protocols. Claude modes without native guidance and every ACP adapter declare queue behavior. Before starting the next provider turn, the supervisor collapses adjacent queued chat entries into one prompt: it keeps the newest complete bounded-history snapshot and appends every exact raw message once in arrival order. Provider admission is not completion, and only the last terminal final/error ends application and supervisor activity. The application converts emitter handoff and terminal completion into balanced, conversation-scoped main-agent activity events for the TUI, Telegram, and WhatsApp. WhatsApp translates that canonical lifecycle into composing only after communication-agent admission and synchronously pauses before terminal or handler-error delivery when the final overlapping reference ends. Telegram starts typing at acceptance, including media and transcription preparation. Both remote transports deliver only the last non-continuing terminal response; the TUI keeps the streamed presentation, and optional CLI streaming exposes deltas.

Accepted human messages also carry private stable source identities. Append-only correlation facts record provider reservation mode, logical execution membership, exact terminal/cancellation coverage, and recovery admission. Telegram and WhatsApp use native message identity; TUI and CLI create an identity before loopback submission. Duplicate source delivery is suppressed.

Every admitted harness job gets a user-facing number from a workspace-local counter and one private atomic snapshot under `.spynel/jobs`. Counter allocation is serialized by a cross-process operating-system lock, atomically persists the number and generation, advances 1 through 9999, and then wraps to 1. A private collision-proof filename and monotonic generation keep retained and even overlapping reused numbers isolated; numeric lookup chooses the newest generation. The allowlisted header carries type, origin category, provider, timestamps, duration, structured final state, and attempt counters without prompts, session keys, conversation identities, attachment paths, notification routing, or public opaque identifiers. The ordered provider-neutral event stream is terminal-control sanitized, centrally credential-redacted, capped at 64 KiB per event and 512 KiB per job, and marked where truncation occurs. Replacing the complete bounded snapshot avoids torn concurrent appends; a crash leaves the last complete snapshot readable and a missing end time is presented as interrupted or still running. The same authenticated shared handler serves chat, direct CLI, TUI, and local terminal API callers. No product code reads archive text, and cleanup removes expired completed or interrupted archives on the conversation cutoff while protecting exact live private archive identities.

Jobs contain one mutex-protected canonical snapshot with structured live execution state and bounded detail/activity/reconnect/recovery fields. Provider adapters publish lifecycle signals rather than making `/jobs` parse prose; Claude Code's transport-only reconnect diagnostic is handled by one anchored adapter mapping. Late events use private never-reused process-local execution handles, so wrapped public numbers cannot revive or mutate another generation. Detailed job inspection joins that snapshot to the current persisted archive, reads at most 2 MiB, exposes an explicit metadata allowlist, sanitizes controls and Markdown metacharacters, bounds rendered content, then rechecks process-local liveness to tolerate concurrent completion. It never reads harness transcripts or emits full session keys. Audio input, models, attachments, complete conversations, and obsolete harness output are disk-backed instead of retained as application state.

Proactive delivery is provider-neutral at the application/channel boundary. Every delivery carries its stable outbox event ID, every origin must name an existing durable conversation, and Telegram or WhatsApp authorization is reapplied. Remote histories record a private sending/sent ledger keyed by that ID; failed and interrupted pre-send attempts remain retryable and ledger controls are excluded from conversation rendering. WhatsApp maps the event ID to `SendRequestExtra.ID`, providing server-side retry deduplication. Telegram deliberately retains the HTTPS Bot API and at-least-once retry semantics: because Bot API `sendMessage` has no caller-supplied idempotency field, a process crash after Telegram accepts a message but before Spynel commits `sent` can cause a rare duplicate. This accepted transport limitation never suppresses an interrupted pre-send attempt. `spynel notify --recent-authorized` resolves only the newest user-active authorized conversation inside the authenticated service and fails closed on multiple remote users, tied activity, groups, revocation, unknown conversations, or no eligible activity. Pending outbox deliveries retry through the ordinary primary maintenance loop.

Cleanup uses a strict older-than cutoff. `/cleanup [days]` defaults to seven whole days and shares one cross-process operation with the primary-only eight-hour automatic cleanup, whose live `workspace.cleanup_retention_days` setting defaults to 30 days. Cleanup protects every conversation leased by an authenticated live TUI, including transition grace, every exact live job archive, and the invoking conversation. It deletes only old histories and validated bounded job archives, then reports removed job files and bytes plus partial errors without touching active work or leases. After a new primary takes ownership, cleanup remains fenced for one full live-lease duration so attached clients can renew into the replacement process; an ownerless plain-CLI cleanup holds the election mutation lock through deletion and runs only when no primary lease has existed outside the durable one-live-lease grace period after a clean release. Startup admission and resume-branch creation through registration are serialized with history deletion.

## Harness lifecycle

The harness supervisor owns at most one running harness and exposes readiness without preventing the rest of Spynel from starting. A missing selection or executable can be recorded for setup when no harness is running. Reconfiguration constructs a replacement before swapping a working harness and refuses to switch while the current harness has active work.

Codex starts one `codex app-server --stdio` process, performs the initialize handshake, and maps stable Spynel session keys to persisted thread IDs. An idle message uses `turn/start`; a message arriving during an active turn uses `turn/steer`; `/stop` uses `turn/interrupt` for that conversation only. `model/list` supplies its model catalog.

Claude Code starts one bounded print-mode process per turn with stream-JSON/partial output. Read-only plan mode and non-privileged unrestricted bypass also use streaming JSON input, so a follow-up written before the result remains in-process guidance; Spynel closes stdin after the result and waits for process exit. Workspace-write uses ordinary text input with accept-edits and shell permission. Because Claude refuses bypass under root/sudo, privileged unrestricted mode likewise uses text input with accept-edits plus an all-tools allow rule and emits a runtime warning. Those text-input modes declare queue behavior, so follow-ups resume the same stored session in the next process. The process is interruptible, documented model aliases form the selector catalog, and exact configured identifiers are preserved. These are Claude-native permissions, not OS sandboxing.

Pi starts one long-lived `pi --mode rpc` JSONL process per active conversation, persists its session file, and uses `steer`/`abort` for active-turn guidance and cancellation. Responses are terminal only at `agent_settled`; `agent_end` may precede retry, compaction, or queued continuation. A settled run with at least one successful assistant message reports only its successful messages, joined by newlines, with the last successful message as the final item: a transient provider failure that Pi retried inside the run leaves its failed-message text in the live stream but out of the settled result, and the terminal error is emitted only when the run produced no successful assistant message. Pi sessions also carry a display name. The first ordinary message that creates a session supplies a best-effort label derived from the accepted user content, and `/pi name <name>` explicitly names an existing session without creating one. Naming is metadata-only, is allowed during an active turn, never changes a session's identity, and reports the provider's normalized name; failures stay out of the turn and reply and are not retried. A private Telegram topic receives the same effective name through one automatic rename that the adapter applies at most once per conversation and process, so a new thread is not left as "New chat" and the user owns the title afterwards. Pi runs with the user's ordinary installation: global extensions and their custom tools and providers, skills, prompt templates, themes, context files, and model/provider settings load normally, Spynel passes no resource-suppression flag or approval override, and project-local Pi resources follow Pi's own standard non-interactive trust decision. The sole added Pi resource is the Telegram note extension, materialized privately under `.spynel/runtime` and loaded additively with one `--extension` argument for `chat:telegram:` conversation processes; its `before_agent_start` adds one namespaced `spynel_telegram` system-prompt section and leaves global and trusted-project `SYSTEM.md` and `APPEND_SYSTEM.md` discovery, ordinary resources, and trust decisions untouched. The note is guidance, not enforcement, and a user extension that returns a forced prompt can override it while extension-triggered model runs may bypass `before_agent_start`. Those Pi resources remain distinct from Spynel executable hooks, which run only from explicitly installed project repositories. Because a trusted extension set can request interactive UI, a blocking `extension_ui_request` dialog receives an immediate explicit cancellation plus one provider-neutral status event, and fire-and-forget UI requests are ignored, so no dialog can stall a headless turn. Read-only mode limits both built-in and extension tools to the `read,grep,find,ls` allow-list. Pi RPC has no stronger native sandbox boundary.

ACP starts the selected alias or custom command once and negotiates stable protocol version 1 over newline-delimited JSON-RPC stdio. Each conversation receives an independent `session/new`, then restart recovery prefers advertised `session/resume` and falls back to `session/load` or a new session. `session/update` streams agent text/tool status, `session/prompt` supplies the terminal stop reason, and `/stop` sends `session/cancel`. Model overrides use advertised session config options. Spynel does not expose ACP thought-level selection because those optional choices arrive only with the created session, after the shared pre-dispatch selection boundary; ACP also defines no standard speed category. Spynel advertises no client filesystem or terminal callbacks and automatically resolves permission requests according to the selected sandbox; an agent that acts without requesting permission remains trusted local code. ACP v1 exposes no in-flight prompt steering, so all ACP profiles use the batched same-session queue.

Stable session keys include:

- `chat:tui:local-<instance-id>` for every running window and `chat:tui:<branch>` after resume;
- `chat:telegram:TG-<user-id>` / `chat:telegram:TG-<user-id>-topic-<thread-id>` for private chats and `chat:telegram:TG-group-<chat-id>` / `chat:telegram:TG-group-<chat-id>-topic-<thread-id>` for groups;
- `chat:whatsapp:WA-<number>` and `chat:whatsapp:WA-group-<group-id>`.

Every harness profile uses a separate private session map. Claude, Pi, and ACP records include a non-secret runtime-policy identity; a changed policy starts a fresh provider session rather than replaying stale permission decisions. Pi stores its provider session-file path, while ACP stores only the opaque session ID. `/clear` first resets the inactive mapping, then clears history; if reset fails, history is preserved. `/new` resets only the harness session and leaves history intact. A narrow build-to-dispatch race is accepted: if a session rotation or policy change lands between prompt construction and dispatch, that turn may start fresh with only the current message, because a false capability answer is always safe.

## Channel lifecycle

The channel supervisor consumes only the newest persisted settings snapshot. A fingerprint change revokes the stale channel's runtime authorization before cancellation and starts a replacement; disabling revokes first and publishes an unconfigured state. Allow-list-aware adapters expose a side-effect-free preflight that runs before the supervisor publishes `connecting`. Invalid authorization is retained as a connection error for that fingerprint, and the first observed live authorization loss wakes the adapter's active run loop so Telegram closes its poll/webhook transport and WhatsApp disconnects; the five-second reconciliation tick does not create a reconnect storm. Telegram permits one teardown-only provider action after revocation, `deleteWebhook`, so shutdown cannot leave a dead local listener registered, while all delivery and other provider calls remain blocked. Other build/start failures remain retryable and become connection errors plus runtime logs. No failed bot is allowed to terminate the TUI or the primary server. Telegram and WhatsApp also receive live settings resolvers and repeat canonical allow-list validation at each inbound and outbound security boundary; constructor snapshots, identity mappings, session databases, group addressing, and prior event authorization are never sufficient.

Telegram and WhatsApp each use a bounded incoming queue. External media streams directly into a private temporary file with a byte cap, fsyncs, and becomes visible through a collision-safe commit only after success. Speech transcription defaults to the ElevenLabs cloud path: the stored attachment streams to the fixed ElevenLabs Speech-to-Text endpoint through its own process-wide serial token with redirects refused, and only a missing or blank effective API key, meaning the stored workspace key and the environment variable both resolve empty, falls back to the cached sherpa-onnx Parakeet recognizer behind one shared serial token for that call. Other provider failures surface as the ordinary failure marker. Miniaudio converts WAV/FLAC/MP3, while a checksummed and packet-bounded Ogg reader feeds Opus voice packets to an in-process pure-Go decoder; both produce bounded mono 16 kHz PCM chunks. Composition resolves `spynel/speech/v1/parakeet` below the OS per-user cache once and injects it into media for the Parakeet path. A cross-process file lock protects validation, checksum-pinned private downloads, and atomic version publication; original attachments and other transient channel state remain workspace-owned.

Telegram conversation identity follows the strict canonical route grammar: `TG-<user-id>`, `TG-<user-id>-topic-<thread-id>`, `TG-group-<chat-id>`, and `TG-group-<chat-id>-topic-<thread-id>`. Absent threads and the General topic (ID 1) keep the base conversation and its history and session; thread IDs of at least 2 receive an independent durable history and harness session. Every route-bound reply, terminal error, typing signal, welcome, native attachment, and proactive event carries its `message_thread_id`, while thread IDs never grant authorization: the current allow-list, verified identity mapping, and `group_mode` policy are reapplied before each provider call and again before each bounded rate-limit and transient-transport retry. A private topic title is renamed through `editForumTopic` at most once per conversation and process: the first automatic trigger is unconditional, a successful rename including `TOPIC_NOT_MODIFIED` is recorded in a bounded in-memory set, a conversation already in the set is a silent no-op, and `/pi name` force-renames. A restart clears the set, so a later automatic trigger can rename once more, and eviction can do the same beyond 1024 conversations; after Spynel's rename the user owns the title. Replies render to Telegram's supported HTML subset as independently valid `sendMessage` chunks of at most 4096 parsed-visible Unicode code points, at most eight messages and 32768 parsed-visible code points per reply, with balanced formatting, deterministic truncation with a visible marker over that budget, and a single plain-text fallback only for a provider HTML entity parse rejection. Terminal replies, terminal errors, and direct handler failures render once at enqueue, including any downstream Pi session notice, into private atomic plaintext records under `.spynel/runtime/telegram-replies/`, bounded at 128 records, 16 per canonical conversation, 512 KiB per record, and 16 MiB per directory, with per-route FIFO, at most four concurrent routes, a first-chunk reply anchor, and a persisted acknowledged-chunk cursor. The primary-term worker owns delivery for the whole owner lifetime, independently of adapter generations, so it resumes persisted records after restart and keeps expiry cleanup and queued delivery running while Telegram is disabled; each record is bound to the verified bot account that created it. It attempts the initial send plus five scheduled rounds at 30 seconds, one minute, two minutes, four minutes, and eight minutes measured from each failure's completion, keeps the plain-text entity-parse fallback inside the round, honors a usable 429 `retry_after` up to 60 seconds by pushing the next scheduled round later, never adding a request beyond those rounds, and reauthorizes the live allow-list, route policy, and original group sender before every stored chunk. Exhausted, permanently refused, and revoked records stay until the one-hour expiry without further sends, a fully confirmed record is unlinked immediately, and capacity or storage refusal never falls back to a direct send. Transcript echoes, welcome messages, and proactive text stay direct one-shot sends: transient timeouts, connection resets, closed connections, and premature EOFs retry at most twice after one- and two-second waits, every attempt reauthorizes the exact route and checks the caller's live context immediately before dispatch, and one complete direct text delivery, including chunking, retry waits, the rate-limit wait, and the fallback, runs inside a three-minute delivery budget that cancellation or shutdown ends. Native attachments stay direct one-shot sends without retries and can arrive before a delayed final text; queued finals can span longer than that budget. Only direct text delivery retries transient transport failures; typing, topic naming, attachments, and polling do not. Failed direct and queued deliveries are logged content-free, and a failed final send never fails the harness job, whose complete response remains in durable job output and history. Because `sendMessage` has no idempotency key, an ambiguous timeout can duplicate one queued or direct chunk, and no path claims exactly-once delivery.

## Process lifecycle

All `serve`/TUI processes rooted at the same state directory participate in one server election. A short-held cross-platform OS file lock serializes each read-check-write decision for `.spynel/runtime/primary.json`; the owner record includes a random process instance ID, PID, loopback endpoint, non-secret environment ID, per-term bearer token, start time, and heartbeat. The environment ID is a SHA-256 digest, domain-separated for this purpose, of a private random token stored in Spynel's OS per-user configuration directory outside the workspace. Ordinary processes using that configuration home keep one ID across application and machine restarts; a macOS host and Docker container, and normally separate containers, use different homes and IDs. Spynel deliberately does not publish or derive this value from a hostname, username, home path, MAC address, raw machine/boot ID, or Linux network-namespace inode. The chosen boundary is the supported same-user installation environment, not a proof of network-namespace equality: deliberately sharing the per-user configuration home across isolated namespaces defeats separation, while separate OS users in one namespace receive different IDs.

The owner renews every five seconds. Other processes check once per second and may replace it only after the heartbeat is 30 seconds old. A known environment-ID mismatch on a loopback lease fails before HTTP dialing with host/container guidance and never makes a fresh owner takeover-eligible. A missing or invalid ID from an older/incompatible owner is treated as unknown: the client may make a bounded ten-second compatibility readiness attempt, reports a sanitized failure, and still waits for normal stale-owner fencing before promotion. Every lease newly acquired by this version contains a validated ID; renewal and handoff preserve it until the next fenced acquisition. Renewal and release verify both instance ID and term token, so a stalled former owner cannot overwrite or remove the winner when it resumes. An idle local TUI can request `/primary`: the owner stops all owner-only loops before writing a fenced reservation, the named requester can acquire immediately, other contenders remain excluded, and the reservation opens to fallback takeover after ten seconds if the target disappears.

The elected owner alone constructs the application service and starts Telegram, WhatsApp, the durable Telegram reply worker, and background services. Every TUI, including the owner's, and transient plain CLI clients use the authenticated loopback API for message/event streaming; TUI clients additionally use screen actions/settings and poll bounded shared state, while CLI clients request typed status on demand. Readiness has a ten-second overall deadline and returns only a categorized last condition; long message streams still use their caller context without that startup deadline because provider work may legitimately take minutes. When an interactive TUI observed an existing fresh owner, it prints a connecting line and then success or a sanitized actionable error before alternate-screen rendering begins. First-owner, headless, redirected, remote-channel, and automation paths do not print those status lines. This keeps harness session persistence and mutable runtime state single-writer. A process records whether a healthy owner existed before joining the election: an initially ownerless winner resumes the latest disk-backed TUI conversation and harness session, while a process that found an owner or lost the initial race starts a unique empty conversation with the welcome banner. A secondary reloads `.spynel/config.yaml` before promotion and keeps its existing conversation identity when ownership changes.

`/restart` is dispatched by the shared application service on every channel. The service persists and emits its final acknowledgment before publishing a coalesced process request. The CLI gives the TUI enough time to render that event, cancels the server context, closes the harness, restores the terminal, and replaces the process in place with the current executable and active server arguments so service-manager identity is preserved. A TUI entered through `spynel init` restarts as the equivalent `spynel serve --tui --config <initialized-file>` invocation instead of trying to initialize the existing workspace again.

The standalone installer records ownership under its per-user installation root, never in a workspace. Verified complete bundles live in immutable release directories; an atomic `current` symlink selects the active bundle. The updater validates bounded SHA-256 downloads, archive paths/types/size, required runtime files and the executable version before publication, under a crash-released installation lock. Existing processes retain their libraries; restart and generated services use the stable entry point. Shared `/update` publishes the validated bundle, acknowledges the action and requests the existing graceful owner shutdown/restart. Interactive script TUIs use the same asynchronous hourly checks against stable GitHub Releases; unmanaged executables and headless commands do not check proactively.

The npm launcher identifies its package root to the Go runtime. Interactive TUI starts query npm's `latest` endpoint with a ten-second total deadline and may prompt for `npm update`; the launcher also passes explicit periodic-check eligibility, the attempted-check timestamp, and any valid latest version into the Go process. The TUI consumes that snapshot instead of immediately repeating the lookup, then uses the shared bounded updater asynchronously no more than hourly. For npm, only an eligible validated launcher-managed process can publish this state; unknown, invalid, equal, older, failed, and non-npm states render no header warning. Noninteractive commands and generated `--automatic-startup` login services carry no eligibility or snapshot state and make no immediate or periodic proactive lookup. Explicit `/update check` checks share the same deadline. `/update` persists its acknowledgment and stops the owner with a dedicated exit code plus the normalized restart arguments, including the `init`-to-`serve --tui` continuation. The supervising Node process then runs the appropriate local/global npm update after the requesting Go process exits. After publication, the shared updater asks every other registered instance of that installation to shut down gracefully and exec the updated binary in place, retaining its PID and terminal descriptors; the launcher then starts the requester. Private per-user records under the OS configuration directory identify each server/TUI by PID, random launch generation, executable, installation and version. Native executable inspection verifies Spynel ownership before signaling, and restart succeeds only after new generations report the target version and application readiness. The registry contains no workspace credentials. Instances from before coordinated restart are rejected explicitly. `spynel killall` shares verified process inspection and bounded TERM/KILL termination with uninstall, and stops matching autostart services without removing their registrations.

## History and memory

Each channel/conversation has an independent append-only JSONL file. Harness context reads backward in 64 KiB blocks and stops at both the configured message and character limits. Prior-history seeding applies only when the provider session does not retain the conversation; the current user message is always rendered, including when either limit is zero, and a positive character limit bounds it. Oversized single records are bounded rather than forcing the complete file into memory.

Each TUI startup and live display is a 500-entry/500,000-rune tail with an explicit omission notice. The first election winner in an ownerless workspace selects the latest TUI history; additional live windows use `tui/local-<instance-id>`, preventing histories or communication harness threads from colliding. A window keeps its selected identity when its process gains or loses ownership. `/resume` scans filenames, reads at most one newest entry for each preview, and returns at most 100 choices. Selecting one captures the source size under its conversation lock, then streams exactly that point-in-time prefix to a new random eight-character TUI branch. The plain `conversations resume` command uses the same copy contract but targets a new `cli/resume-<short-id>` branch. Only bounded display/query tails are loaded; the complete copied JSONL remains on disk. Remote channels continue using their stable histories and are never rewound.

Operational logs pass through an attributed application boundary that removes controls, redacts common credential forms, and bounds entries before appending private per-session JSONL under `.spynel/runtime/logs`. Harness, extension, media, channel, job, configuration, and top-level command failures use that boundary. Subprocess diagnostics are bounded and captured while intentional JSON protocol stdout, CLI response output, and user content remain on their dedicated streams and are not logged. In particular, startup registration helpers and extension Git installation retain separately attributed stdout/stderr plus exit status, cap each stream at 64 KiB, and omit command arguments so repository URLs or scheduler actions cannot become log metadata. The application chronologically merges overlapping session files into a newest-4,096-entry view with deterministic source-file and record-position tie-breaking, ignores corrupt or partial records, rotates at 2 MiB with eight-file retention, and treats persistence failure as non-fatal. Restore, append, clear, and close failures create non-recursive in-memory diagnostics so `/log` exposes when durable crash evidence is unavailable. Errors and clean session boundaries are synced where feasible; `SIGKILL`, power loss, and diagnostics emitted directly by native libraries below Go's writers remain unable to guarantee a final captured record. Runtime updates use newest-only channels.

Routine informational persistence uses a bounded non-blocking worker; error, fatal, partial-tail, and session-boundary records use acknowledged flushes. Queue admission, acknowledgements, control operations, shutdown, and directory-lock acquisition have a two-second bound, after which Spynel continues with the in-memory view and a persistence diagnostic. The runtime serializes append admission with clear so a record accepted before `/log clear` cannot reappear after restart. A directory-scoped operating-system lock serializes rotation across processes without allowing a lock holder to stall startup indefinitely, and each active session file remains locked for its open lifetime so retention never unlinks another process's evidence. Owned goroutine boundaries and the configured CLI process boundary retain panic stacks before preserving panic semantics; a panic before any workspace configuration can be resolved has no safe durable destination and remains terminal-only.

## Configuration save and reload

Commands and forms clone the current config, parse every change, validate the complete result, atomically persist it, and reload the saved canonical file into shared process memory before returning. The public harness contract contains `name`, `model`, and `sandbox`, plus `acp_command`/`acp_args` only for the explicit custom ACP profile. Model and reasoning effort accept manual identifiers independently of discovery, while service modes remain capability-validated. Built-in commands, working directory, approval policy, and network flag are derived during composition; arguments never pass through a shell. Profile and sandbox values must match their exact current catalog choices after lowercase and edge-whitespace normalization; unrestricted access is the default. Harness implementation and sandbox replacement require idle state. Model persistence instead shares a supervisor fence with provider-dispatch admission: work admitted before the commit retains its snapshot, while dispatches admitted after it, including continuations, use the new model without restarting active work. Startup registration refreshes after reload. Secret values never enter replies, status, or durable command history.

## Extension direction

New built-in transports implement `channel.Channel`. New coding agents add one catalog/factory entry, implement `harness.Harness`, and explicitly declare native steering or queue behavior. ACP-compatible agents normally need only a command/argument alias around the shared adapter; other adapters own their protocol translation. Queue-mode chat bursts are batched automatically. Project extensions remain executable hooks with JSON stdin/stdout so they are portable across languages and Go versions. They are intentionally trusted code rather than a misleading partial sandbox.
