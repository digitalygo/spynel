# DOX framework

- DOX is the AGENTS.md hierarchy used by this project.
- Agents must follow the applicable AGENTS.md chain before editing files.

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees.
- Durable docs, source files, prompts, tests, and packaging metadata must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it.
- Spynel is the Go application rooted in this repository. It owns chat transports, harness sessions, persisted runtime state, executable project extensions, documentation, and distribution.
- Describe Spynel consistently as a classic, non-AI program that coordinates and oversees external AI/coding harnesses. It is not itself an agent and does not compete with or duplicate harness intelligence. The product relationship is one human through one assistant-facing relationship to many agents; “One human → one agent → infinite agents” is a conceptual expression of scalable leverage, never a literal resource guarantee. Use “Simplicity at scale.” as the primary slogan and “Simplicity. Leverage. Quality.” as the defining words. Do not invent capabilities, integrations, guarantees, or adoption claims when adapting this positioning to public copy.
- The retired Python prototype and the former nested Go layout are not part of the repository. Product behavior, tests, documentation, packaging, and automation use root-relative paths.
- Produce one cross-platform application that hosts the styled TUI, long-running communication channels, coding-harness sessions, and project extensions. Release archives include the sherpa-onnx native runtime beside the executable.
- `cmd/spynel` is composition only. Channels translate external messages into the provider-neutral application contract and never call a coding harness directly.
- Every channel conversation has an independent harness session and durable history.
- Accepted human conversation messages carry private stable source identities and append-only execution/admission/terminal/cancellation correlation.
- Every running process in one workspace participates in a single primary-server election. The owner alone runs Telegram, WhatsApp, and background services; every TUI reaches the owner's application service over an authenticated loopback API. Primary leases carry a non-secret digest of a private per-user/per-environment installation token so a client rejects a known-foreign host/container loopback before dialing; missing or invalid identifiers remain fresh-owner fenced and receive only bounded compatibility readiness. Interactive secondary TUI startup reports connection progress before entering the alternate screen, while automation remains quiet. The first TUI in an ownerless workspace resumes the latest TUI communication session, while additional live TUIs receive independent sessions. Five-second heartbeats, a 30-second stale threshold, lock-free discovery of atomically published leases, serialized compare-and-replace takeover, and target-fenced `/primary` handoffs prevent duplicate owners while allowing secondary startup, explicit promotion, or recovery from a dead or stalled server.
- Task/goal Markdown workflows, workflow scanning, claims, leases, review and recovery, the semantic workflow heartbeat, the notification agent, and autonomous unresponded-message scans are retired product behaviors. The retired `internal/orchestrator` and `internal/instructions` packages have been removed from the repository. Existing workspace task/goal documents, prompts, instruction files, histories, and credentials remain untouched and inert on disk.
- Runtime state, histories, WhatsApp credentials, installed extensions, and the canonical user configuration `.spynel/config.yaml` belong inside each initialized workspace's fixed `.spynel/` directory. Relative configuration paths resolve from the workspace root, and no configurable state-directory key exists. Installation identity and live process-control records belong in the OS per-user configuration directory. Automatically managed speech models live in the operating system's per-user cache under Spynel's versioned speech namespace and are shared across compatible workspaces for that user; that local model lifecycle belongs to the Parakeet backend, whether selected explicitly or used as the default provider's missing-key fallback. The default `elevenlabs` provider streams accepted audio to the ElevenLabs Speech-to-Text API, resolves its API key from the stored `speech.elevenlabs_api_key` in the private workspace configuration first and then from the named environment variable, stores only an explicitly provided key in that private configuration, and falls back to local Parakeet only when both sources are missing or blank at transcription time; a nonblank stored key is authoritative, and every other provider outcome surfaces as the ordinary failure marker.
- Spynel is alpha software and supports only its current configuration, state, manifest, session schemas. Validate current setting values and reject obsolete state, manifest, and session representations. Ignore unused configuration keys on load without rewriting the file; ordinary canonical saves remove them. Do not retain configuration migrations or fallback readers. Prefer one clear current representation over preserving pre-release data.
- There is no OpenAI-compatible HTTP façade. Channels, harnesses, and trusted executable hooks are extended through explicit interfaces.

## Read Before Editing

1. Read the root AGENTS.md.
2. Identify every file or folder you expect to touch.
3. Walk from the repository root to each target path.
4. Read every AGENTS.md found along each route.
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there.
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules.
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX.

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately.

- Keep application code harness-neutral. Codex, Claude Code, Agent Zero CLI, Pi RPC, and ACP behavior belongs in `internal/harness`; future harnesses register metadata/factories there, implement the same interface, and explicitly declare native-steer or queued follow-up behavior. Pi RPC loads the user's ordinary global extensions, skills, prompt templates, themes, context files, and model/provider settings, leaves project-local resource loading to Pi's own standard non-interactive trust decision instead of Spynel suppression flags or an approval override, and cancels unsupported interactive extension dialogs rather than hanging. ACP-compatible CLIs normally use one concise command/argument alias around the shared v1 stdio adapter; only the explicit custom ACP profile accepts a user command and shell-free argument list. - Pi native ordinary chat receives the raw accepted current user message byte-for-byte on both fresh and retained sessions, with no bounded Spynel history seed and no durable-history path injected. The optional provider-neutral `NativeConversationInputProvider` capability keeps application code harness-neutral; every other harness and non-native session key keeps the provider-neutral bounded history context, whose prior-history seed is disabled when the optional provider-neutral `ConversationContextProvider` capability reports that the provider session already retains the conversation, and absence, uncertainty, or any other safe-false capability answer keeps the bounded seed. The current user message is delivered in every chat prompt, including with zero history limits.
- Pi session controls are the only harness-specific user commands. `/pi session` reports the full current session ID and a shell-safe `pi --fork <absolute-session-file>` command; fork is deliberate because Pi JSONL session files have no cross-process lock, so direct Pi and Spynel must never open the same session file concurrently. `/pi compact [instructions]` compacts an existing idle session with optional instructions of at most 4096 Unicode code points and reports bounded token counts without creating or replacing a session. `/pi import <full-session-id>` accepts only a full canonical lowercase UUID, performs bounded read-only discovery of the effective Pi session stores, requires a supported regular JSONL header with the exact ID and a matching working directory, forks the validated source into `.spynel/runtime/pi-sessions`, and leaves the source unchanged. `/pi name <name>` assigns one explicit 1-to-128-code-point single-line name to an existing session, is allowed during an active turn, force-renames a private Telegram topic even when Spynel already renamed it, never creates a session, and reports a failed topic rename as partial success without rolling the provider name back. The first user message that creates a Pi session derives a bounded best-effort label, applies it to the session through the provider's existing-name-preserving path, and triggers one unconditional automatic private Telegram topic rename that the transport performs at most once per conversation and process, so a new thread is never left as "New chat" and the user owns the title afterwards; rotation, import, resume, and steering never name a session, and naming failures never affect the turn or reply and are not retried. Optional provider-neutral session inspector, namer, compactor, and importer interfaces keep application code harness-neutral, and only Pi implements them. These controls are available only in the local TUI and canonical private Telegram conversations; groups, forum topics, the plain CLI, WhatsApp, malformed routes, and other channels refuse before any capability call and never receive a session ID or path.
- The first successful non-continuing final response after an ordinary TUI or private-Telegram prompt that creates or rotates a Pi session gets a prepended full-ID notice and `/pi session` hint. The notice is added downstream of extension hooks, media processing, durable history, and job archival, so it never enters durable or model-visible history; it never appears on errors, resumed or imported sessions, groups, or other channels.
- Keep every harness scalar under `.spynel/config.yaml`'s `harness` section and require exact current catalog names and sandbox values after case/edge-whitespace normalization. The retired workflow keys `harness.reviews`, `harness.chat_agent_prefix`, `harness.developer_agent_prefix`, `harness.reviewer_agent_prefix`, and `harness.heartbeat_agent_prefix` are ignored on load like any unused key and disappear from the next canonical save; they never affect dispatch.
- Treat model, reasoning effort, and service mode as one atomic active-safe dispatch snapshot. Detected choices come from provider/model metadata; model and supported-harness effort pickers end with Custom text entry, available even when discovery fails. Explicit model/effort identifiers bypass discovery membership checks and let the harness validate support. Service modes remain capability-validated, ACP effort remains unsupported, and a model change clears stale properties to inherit unless an effort is explicitly supplied in that transaction.
- Keep all exposed non-extension settings live behind the shared save-and-reload boundary. The only restart-bound settings are `extensions.enabled`, `extensions.directory`, and `extensions.hook_timeout`. A validated save atomically replaces canonical YAML, reloads that file into the shared process snapshot before returning, and publishes the refreshed snapshot to runtime owners; use minimal direct hooks only for owners that cache derived state. Model selection commits under the same fence as harness dispatch admission: admitted turns retain their captured model, including active native steering, while every provider dispatch snapshot ordered after the commit uses the new model, including queued continuations. Harness implementation, command, arguments, and sandbox changes remain transactional and idle-only. Subsequent operations read the refreshed snapshot, while active channels and in-flight turns may finish under their admitted state. Bare `spynel` deterministically launches the TUI; `spynel serve` is headless unless `--tui`, and the retired `channels.tui.enabled` input is normalized away rather than retained.
- The default CLI command is `spynel`; the project configuration file is `.spynel/config.yaml`.
- The supported v1 integration uses the elected application service: request-correlated HTTP/NDJSON messages, bounded committed conversation subscriptions and cursor replay from existing history, atomic bounded resynchronization, and ordinary outbox notifications. An optional private authenticated Unix socket supplements loopback without changing foreign-environment election fences or TUI conversation identity. Headless operational stderr mirrors only content-free lifecycle metadata through the existing runtime logger.
- Keep the plain CLI equivalent to the non-visual application control plane: named disk-backed conversations, bounded streaming/NDJSON message input, active-turn follow-ups, structured status, conversation inspection/branching, attachments, shared slash commands, and trusted extension hooks must use the same application service as interactive channels.
- Authenticated workspace operators see one global live and archived job set through Telegram, WhatsApp, TUI, CLI, and the shared application/API boundary. Assign jobs workspace-local durable numbers from 1 through 9999, wrap to 1, and preserve a job's number through recovery and archival. Numeric lookup selects the newest generation after reuse; collision-proof archive identities remain private. Workspace-local job archives retain bounded redacted event streams through the chat-history retention boundary; they are inspection-only. Conversation identity, creation channel, and durable `notify.origin` are delivery metadata, never inspection or control ACLs. Preserve transport and loopback authentication before the shared handler, prevent cross-workspace archive reads, and expose only bounded privacy-safe projections without conversation IDs, prompts, session keys, notification origins, or arbitrary durable fields.

Stable topic/section references, deterministic bounded text/JSON output, concise `/help` metadata, and repository documentation must be validated together; static docs never read or impersonate live workspace state.

No event carries an automatically supplied stable `event_id`, no per-extension success receipt is persisted, and the runner performs no retry; an invocation can repeat when the caller retries the surrounding operation. Consumers must make visible effects idempotent with their own keys when needed, and no exactly-once guarantee is claimed.
- Known Spynel slash commands remain deterministic and routed through the shared application service; a known command that refuses a surface or lacks authorization still refuses. Unrecognized slash input is not categorically rejected: when the active harness can interpret it, the raw input reaches the harness so Pi can expand its own native skill, prompt-template, and extension commands through its ordinary prompt pipeline. The Telegram Pi system-prompt note is written by one embedded Spynel Pi extension loaded additively with `--extension` on `chat:telegram:` sessions and is never prepended to slash user input.
- Harness chat dispatch delivers accepted user content without Spynel-injected persona, workflow, documentation, scope-discipline, or honesty boilerplate. Pi receives the raw accepted user text, and its native system prompt, resources, extensions, skills, prompt templates, context files, provider settings, and project trust decisions remain authoritative. Only Telegram Pi RPC sessions load one embedded final-replies note extension additively with `--extension`, and its `before_agent_start` writes exactly one namespaced `spynel_telegram` system-prompt section: the user sees final replies only, so any clarification or approval request must be one final question that ends the turn, and the next user reply continues the same Pi session with no artificial pause state. Because the load is additive, Pi keeps discovering global and trusted-project `SYSTEM.md` and `APPEND_SYSTEM.md` files, the accepted user text stays raw, and no extra model or agent turn is added. The note is guidance, not enforcement: a user extension that returns a forced prompt can override it, and extension-triggered model runs may bypass `before_agent_start`, so Spynel claims no model-compliance guarantee. Other harnesses remain functional and receive no additional system-prompt note.
- `spynel notify` and its application/API request remain ordinary explicit outbound delivery. The request requires exactly one of a known durable origin or the mutually exclusive `--recent-authorized` resolver, revalidates remote authorization, persists attempts under `.spynel/runtime/outbox`, and exposes only the durable event ID. Recent-authorized routing resolves only the newest user-active authorized conversation and fails closed on multiple remote users, tied activity, revocation, unknown conversations, groups, or no eligible activity. It is a minimal resolver and delivery primitive with no reminder, scan, or agent policy. Pending outbox deliveries continue through the existing path; no autonomous task agent runs.
- `/cleanup [days]` defaults to seven whole days and shares one cross-process operation with the primary-only eight-hour automatic cleanup, whose live retention setting defaults to 30 days. Cleanup uses strict older-than eligibility, protects every authenticated renewable live-TUI conversation lease (including transition grace) and every exact live job archive, serializes startup admission and resume branch creation-through-registration with history deletion, and remains fenced for one full live-lease duration after owner acquisition while attached clients renew into the replacement process. An ownerless plain-CLI cleanup also holds the election mutation lock through deletion and runs only when no primary lease exists outside the durable one-live-lease grace period after a clean release. Cleanup deletes only old histories and validated bounded job archives. Cleanup reports removed job files and bytes plus partial errors without touching active work or leases.
- Enabled Telegram and WhatsApp transports require valid canonical sender allow-lists and fail closed at configuration, supervisor preflight, adapter startup, every live inbound event, and every outbound/provider boundary. Each adapter resolves the current list rather than trusting its constructor snapshot; missing, malformed, unavailable, or revoked authorization publishes a persistent error, terminates the active listener/socket, and is not reconnect-retried until configuration changes. Telegram teardown may call only `deleteWebhook` after revocation so a stopped listener is never left registered; all useful provider traffic remains blocked. Persisted credentials, sessions, Telegram identity mappings, prior event authorization, group addressing, and self-chat identity never grant access alone. Telegram may persist a minimal identity learned only from an allow-list-authenticated private inbound update so username-authorized users retain stable numeric proactive origins, but every application and delivery check must reapply the current allow-list and fail closed on absent or corrupt identity state.

The transcript-echo family is a separate, explicit outbound path with transcript-only content, not an agent response: when the default-on live `speech.transcript_echo` is enabled, one successful transcription is sent to the same chat or topic as a standalone literal generated-transcript message before the message is dispatched, and its delivery failure never affects the turn.
- Telegram topic routing is automatic and default-on with no configuration setting. Canonical conversations are `TG-<user-id>` and `TG-<user-id>-topic-<thread-id>` for private chats and `TG-group-<chat-id>` and `TG-group-<chat-id>-topic-<thread-id>` for groups and forums. Absent threads and the General topic (ID 1) keep the base conversation and its existing history and harness session; every thread ID of at least 2 receives an independent application and harness session, including Pi. Thread IDs never grant authorization: the current live allow-list, verified username mapping, and `group_mode` policy are reapplied at every inbound and outbound boundary, including every bounded rate-limit and transient-transport retry attempt. Replies, terminal errors, typing, welcome messages, native photo/document attachments, and proactive events remain in the originating topic.
- Telegram renders agent Markdown to its supported HTML subset and delivers it as independently valid `sendMessage` HTML chunks: at most 4096 parsed-visible Unicode code points per message and 32768 parsed-visible code points across at most eight messages per reply. Formatting stays balanced across chunk boundaries, an entity spelling or Unicode code point is never split, grapheme boundaries are preferred while the remaining reply budget allows, and an over-budget reply is truncated deterministically with a visible marker while full durable history is preserved. Only a provider HTML entity parse rejection retries that one chunk once as plain text. Terminal final responses, terminal errors, and direct handler failures render once at enqueue, including any downstream Pi session notice, and persist as private atomic plaintext records under `.spynel/runtime/telegram-replies/` bound to the verified bot account: at most 128 records, 16 per canonical route, 512 KiB per record, and 16 MiB per directory, with per-route FIFO, at most four concurrent routes, a first-chunk reply anchor, and a persisted acknowledged-chunk cursor. The primary-term worker sends an initial attempt plus five scheduled rounds at 30 seconds, one minute, two minutes, four minutes, and eight minutes measured from each failure's completion, keeps the entity-parse plain-text fallback inside the same round, honors a usable 429 `retry_after` of at most 60 seconds by pushing the next scheduled round later, never adding a request beyond those five rounds, and reauthorizes the live allow-list, exact route, and original group sender immediately before every chunk. Exhausted, permanently refused, and revoked records stay until the one-hour expiry, a confirmed final chunk unlinks the record, and no part of this is configurable or guaranteed after one hour, queue capacity, or storage failure. The worker runs for the whole primary term even while Telegram is disabled, resumes persisted records after restart, and logs failures content-free. Transcript echoes, welcome messages, and proactive text remain direct one-shot sends: transient `sendMessage` timeouts, connection resets, closed connections, and premature EOFs retry at most twice after one- and two-second waits, one bounded rate-limit retry honors `retry_after` up to 60 seconds, every attempt rechecks the exact current route authorization and the caller's live context before dispatch, and one complete direct text delivery (transcript echo, welcome, or proactive message), including chunking, retry waits, the rate-limit wait, and the plain-text fallback, shares a three-minute delivery budget that caller cancellation or shutdown ends. Native attachments remain direct one-shot sends without retries and can arrive before a delayed final text; queued finals can legitimately span far longer than three minutes. Only direct text delivery retries transient transport failures, while typing, topic naming, attachments, and polling never do. Persistent rate limits and other non-transient failures remain visible errors. Because `sendMessage` has no idempotency key, an ambiguous timeout can duplicate one queued or direct chunk and no path claims exactly-once delivery; a failed final send never fails the harness turn, whose complete response remains in durable job output and history. A reply whose send failed before the durable queue existed, such as the one archived as job 388, is never backfilled, while a queued reply is retried on its bounded schedule regardless of job completion.

## Verification

- Run `scripts/dev.sh dox` after changing repository structure or any `AGENTS.md`; the smoke test also runs this deterministic coverage and index gate through the pinned Go toolchain.
- Run `go test ./...`, `go vet ./...`, and `mkdir -p .tmp-bin && go build -o .tmp-bin/spynel ./cmd/spynel` before handoff after Go changes.
- `scripts/dev.sh test` also checks the locally replaced Bubble Tea module, whose nested tests are excluded by `./...`; changes to that terminal boundary require its race tests plus the real TUI PTY test.
- Run `scripts/smoke.sh` after changes to initialization, configuration, harness dispatch, extension loading, or channel lifecycle.
- Run `node npm/test.js` after npm launcher or release-layout changes.
- Run `scripts/package-native.sh` for the host target and execute the extracted archive after packaging or release-workflow changes; the release workflow compiles every supported target on a matching native runner.
- Ordinary Go test, race, vet, build, smoke, implementation, and review commands reuse Go's shared user cache. Do not assign `GOCACHE` to a project-local or per-command directory; Go action IDs already isolate flags, targets, tags, and toolchains.
- A deliberately requested cold-cache diagnostic must use `scripts/cold-cache.sh`, which creates a unique cache outside the project and removes it after the complete diagnostic process tree terminates. Cold-cache runs are for investigating suspected cache-dependent behavior, not routine verification.
- Write disposable verification binaries and profiles to test-managed temporary directories and clean them when the command finishes. If evidence must survive between implementation and review, keep it only under the ignored `.tmp-artifacts/<task-id>/` directory, record it in the task, and remove it when review no longer needs it.
- Use only purpose-specific repository-local `.tmp*` directories for developer toolchains, captures, scratch data, and temporary retained evidence. They are ignored disposable state and must remain safe to remove wholesale; never keep durable source or workflow state there.

- Updates apply by default: shell `spynel update` selects its installation independently of workspace ownership; shared `/update` selects the primary's installation. Both restart all registered servers and TUIs of that installation across workspaces, even when already current. `update check` is read-only. The updater owns private per-user process-control records outside workspaces, verifies native executable identity, and requires a new process generation at the target version with application readiness before reporting restart success. Older unregistered instances require an explicit one-time stop/relaunch. `spynel killall` stops all verified Spynel processes the caller can control and matching autostart services, preserving workspace data and future startup registrations.

- Native process discovery must retain visibility after npm unlinks a running image. On macOS, use the retained executable-path field from `kern.procargs2` when `proc_pidpath` loses the vnode path; never expose its arguments or environment. An unreadable live registered process is an explicit error, never an omitted restart target.
