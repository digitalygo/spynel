# Pi-direct chat rework and workflow retirement

## Summary of changes

This operation records the completed, user-authorized Pi-direct rework on top of `8425af2` on `main`. The delta retires the workspace task/goal workflow layer and routes ordinary chat prompts directly to the executing harness: the `internal/orchestrator` and `internal/instructions` packages, task/goal/review/semantic-heartbeat/notification-agent/automatic-recovery behaviors, the workflow configuration keys and templates they depended on, and their commands, API surface, and documentation were removed. At the same time, Pi ordinary chat now receives the raw accepted current user message with no Spynel persona, no durable history path, and no bounded history seed; unknown slash input reaches Pi's native prompt pipeline while known Spynel commands stay deterministic; and one embedded Pi extension loaded additively with `--extension` supplies the Telegram-only final-reply note.

The delta spans 165 paths: 149 tracked files changed or deleted and 16 new files under `internal/`. Existing workspace documents, configuration, histories, and credentials were left untouched and inert. The work is uncommitted on top of the baseline and is not part of the published `v1.6.0` release.

## Technical reasoning

### Workflow layer retirement

The workflow layer duplicated coordination intelligence that belongs to harness sessions. Spynel is a classic, non-AI program that coordinates and oversees external harnesses; it should translate channel messages into provider-neutral dispatches and own transport, session, and durable runtime state rather than host its own task/goal planning, review, heartbeat, and notification agents. Removing `internal/orchestrator` and `internal/instructions` also removed the provider-lock, retention, review-policy, route, status, work-list, and workflow code that only served those behaviors.

Workspace data was treated as historical. The implementation never scans, rewrites, or deletes existing task/goal files, prompts, configuration, or credentials, and the new `internal/app/retired_workflow_test.go` pins sentinel files as unwritten and unremoved with unchanged permissions. The retired `harness.reviews` and `harness.*_agent_prefix` keys are ignored on load like any unused key and disappear on the next canonical save, which follows the no-migration policy: one current representation, no fallback readers.

### Direct Pi prompts

Ordinary chat dispatch no longer injects persona, workflow, documentation, scope-discipline, or honesty boilerplate. Pi receives the raw accepted current user message byte-for-byte on both fresh and retained sessions, with no bounded Spynel history seed and no durable history path. The optional provider-neutral input capability keeps `internal/app` harness-neutral, so only Pi changes behavior. A known Spynel slash command still routes deterministically through the shared application service and still refuses when the surface or authorization disallows it, while unrecognized slash input is passed through as raw text so Pi can expand its own skills, prompt templates, and extension commands through the ordinary prompt pipeline.

Every other harness and every non-native session key keeps the provider-neutral bounded history context. Its prior-history seed follows the existing `ConversationContextProvider` capability, and absence, uncertainty, or any other safe-false answer keeps the bounded seed. The current user message is delivered in every chat prompt, including when history limits are zero.

### Telegram Pi note

The note is one embedded, dependency-free Pi extension materialized into the private workspace runtime directory and passed with a single additive `--extension` argument for `chat:telegram:` Pi RPC sessions only. Its `before_agent_start` handler writes exactly one namespaced `spynel_telegram` section into the structured system prompt: the user sees final replies only, so any clarification or approval request must be one final question that ends the turn, and the next user reply continues the same Pi session with no artificial pause state.

Additive loading is the deliberate choice. `--append-system-prompt` was rejected because it suppressed Pi's trusted and global `APPEND_SYSTEM.md` discovery. A real Pi run with the fake provider verified that the additive extension path preserves that discovery parity while still delivering the note, and Pi keeps loading global extensions, skills, prompt templates, themes, context files, and model/provider settings, with project-local resource loading left to Pi's own standard non-interactive trust decision. The note is guidance, not enforcement: a user extension that returns a forced prompt can override it, extension-triggered model runs may bypass `before_agent_start`, unsupported interactive extension dialogs are cancelled rather than left hanging, and Spynel claims no model-compliance guarantee.

### Extension trust boundary

The materialized extension file lives inside the workspace `.spynel/runtime` tree. Before any launch, the state root and the runtime directory beneath it are each validated by `Lstat` as real, current-user-owned directories with no group or other permission bits; a missing directory is created `0700`, and a pre-existing directory that violates that private trust contract fails the launch closed instead of being chmodded or replaced. An existing extension file is reused only when it is a regular non-symlink file with exactly the embedded bytes, private permissions, and current-user ownership. Anything else is repaired through a `0600` temporary file and one atomic rename that never follows the target, concurrent launches materialize identical bytes, and a directory occupying the target path fails the launch instead of being deleted. This closes the security review finding about launching a Pi extension from a directory the user does not exclusively control.

### Preserved behavior

The TUI, Telegram, WhatsApp, and plain CLI channels stay, as do the other harnesses. The authenticated primary election and loopback service boundary, ordinary job and status surfaces, explicit `spynel notify` outbox delivery with its 30-second pending retry through the primary maintenance loop, the existing eight-hour automatic history and job-archive cleanup, speech transcription and media handling, and the Pi session controls (`/pi session`, `/pi compact`, `/pi import`, `/pi name`) are unchanged. Conversation identity, session naming, Telegram topic routing, rich-text chunking, transcript echo, and rate-limit answer recovery are untouched.

### Legacy sessions and residual effects

Legacy retained Pi sessions may still contain old dispatcher messages from before the rework, because Spynel does not rewrite provider session files. `/clear` deletes that conversation's durable history and resets its provider session if the user chooses. The retired workspace documents remain inert on disk.

## Impact assessment

- The product model is now enforced in code: the elected owner's background loop only retries pending explicit outbox deliveries and runs history and job cleanup, and no orchestrator, semantic heartbeat, notification agent, or autonomous unread-message scan exists.
- Ordinary Pi conversations receive exactly the accepted user text. Other harnesses and every non-native session key keep the bounded history seed and its safe-false capability rules, so their behavior does not regress.
- Known framework commands remain deterministic across channels, while unrecognized slash input no longer stops at Spynel and can reach Pi's own command expansion.
- Telegram Pi sessions carry one final-reply guidance note loaded additively. Because it is guidance only, user extensions and extension-triggered runs can override or bypass it without changing Spynel behavior.
- Existing workspace task/goal documents, prompts, histories, and credentials remain on disk and inert. Retired configuration keys are ignored on load and removed by the next canonical save, with no migration and no rewriting of untouched files.
- The repository structure shrank by two packages and their DOX files. `docs/persistent-instructions.md` and `docs/tasks-and-goals.md` were removed, the root and package `AGENTS.md` contracts were updated, and the new `internal/agentdocs/catalog_sync_test.go` keeps the static documentation command list and the canonical slash catalog in lockstep in both directions.
- Documentation for architecture, harness compatibility, integrations, configuration, extensions, CLI, programmatic integration, and the provider canary threat model was synchronized with the new boundaries and the extension trust validation.
- No commit, push, release, or deployment was performed. Nothing in this record claims that the rework is available to installed users.

## Validation steps

- Baseline: at task start `HEAD` was `8425af2` on `main` with a clean tracked tree. The only untracked, non-ignored path predating the task was the private `.ai-telemetry/` directory, which was never inspected, staged, modified, or packaged.
- Because that untracked directory makes the repository-wide DOX and smoke gates fail for reasons unrelated to the change, the exact delta was copied into a clean detached Git worktree and all repository-wide validation ran there.
- Repository gates passed: `scripts/dev.sh dox` reported DOX coverage valid for 49 tracked directories, and `scripts/dev.sh test`, `go test ./...`, `go test -p1 -count1 ./...`, `go vet ./...`, a Go build of `./cmd/spynel`, `scripts/smoke.sh`, `node npm/test.js`, and `git diff --check` all completed without failures.
- Packaging: `npm pack --dry-run` listed nine files and no telemetry artifacts.
- Targeted race runs passed for `internal/app`, `internal/harness`, `internal/localapi`, `internal/workspace`, and `internal/config`. The TUI race run passed with the strict p95 latency threshold excluded under the race detector, the real TUI PTY race test passed, and the replaced Bubble Tea module's nested race tests passed. The normal p95 latency test passes in regular `go test`.
- New-behavior coverage: `internal/app` at 83.7%, notification-origin normalization at 100%, `Process` and `Enqueue` above 95%, Pi slash handling at 100%, private extension directory validation at 83%, and the extension materializer at 75% because the remaining OS I/O failure arms are not injectable.
- The hybrid quality judgment passed twice. The security review finished at full PASS after two blocked findings were fixed and re-reviewed: an untrusted Pi extension directory, fixed by the private runtime ownership and mode validation described above, and a malformed outbox `Attempts` panic, fixed and followed by a `MaxInt-1` repeated-delivery advisory fix.
- An unrelated pre-existing test data race in `internal/app/runtime_log_test.go` was fixed without a production change.
